# Gotchas

- **WebAuthn does not exist in webkit2gtk-4.1 as shipped by Debian 13 (tested 2.52.5).** `PublicKeyCredential` is undefined; there is no `enable-webauthn` property and no WebAuthentication feature flag (verified via GIR and a live JS probe). Upstream only builds WebAuthn for the GTK4 port (webkitgtk-6.0), which wry/Tauri cannot use yet. That is why the app ships its own implementation (polyfill + Rust CTAP2 client); see architecture.md.
- **Microsoft hides the passkey option based on user-agent sniffing.** With WebKitGTK's default UA the login page shows "Use an app instead" and never calls any WebAuthn API, even when `PublicKeyCredential` exists. The Chrome-on-Linux UA set in main.rs is load-bearing; remove it and passkey sign-in silently disappears with no error anywhere.
- **main.rs still sets `enable-webauthn` via GObject property, guarded by `has_property`.** Future-proofing only: if a WebKitGTK build ever ships the property, native WebAuthn gets enabled too. Keep the guard: `set_property` on a missing property is a hard panic.
- **The ACL permission is autogenerated.** build.rs declares `webauthn_get_assertion` in the app manifest, which generates `permissions/autogenerated/` (gitignored). Without the build.rs declaration, remote pages get a permission error on every invoke: remote origins always go through the ACL.
- **Polyfill runs in the main frame only.** Tauri injects its IPC internals main-frame-only, so an iframe-embedded login flow would see a polyfill with no IPC; the polyfill is therefore main-frame-only on purpose. If Microsoft ever moves sign-in into an iframe, this breaks.
- **Sign-in only.** `navigator.credentials.create()` throws NotSupportedError. Register new keys in a regular browser, then sign in here. USB keys only; no phone QR (hybrid) flow.
- **`frontendDist` is a URL on purpose.** There is no local dist folder. Tauri accepts a URL here for remote-only apps; do not "fix" it by adding a dist directory. Side effect: outlook.office.com counts as a *local* URL in the ACL, which is why capabilities/webauthn.json uses `local: false`.
- **Never launch with `WEBKIT_DISABLE_DMABUF_RENDERER=1` by default.** It forces WebKitGTK onto software rendering and makes the whole app sluggish (confirmed on Intel iGPU: dropping it closed most of the perceived gap to Electron wrappers). It is first aid only, for a blank window on a broken GPU stack, and belongs in a user's environment, not in the app or docs examples.
- **The custom main.desktop template exists because of a missing `%u`.** Tauri's default .desktop template adds the mailto MimeType from the deep-link config but generates `Exec=outlook-for-linux` without `%u`, so a clicked mailto link would launch the app with no URL argument. If you drop the template, mailto handling silently breaks; verify by extracting the .deb and reading the Exec line.
- **mailto flow**: the .desktop registers x-scheme-handler/mailto; a second launch is forwarded by the single-instance plugin to the running app, which opens a compose window via OWA's deeplink URL. Sequential window labels (compose-0, compose-1) are required: reusing a label is an error while the old window exists.
- **OWA never raises web notifications here; the app fakes them from the DOM.** Its service worker disqualifies WebKitGTK before ever calling showNotification (no push service), and WebKitGTK would not deliver service-worker notifications to the embedder anyway (only the page-context `Notification` constructor reaches the show-notification signal; verified empirically). The OWA notification setting is therefore irrelevant. `unread_title.js` polls the folder pane and message list instead; see architecture.md.
- **New-mail parsing is anchored to English OWA labels.** "Inbox", "unread" and the aria-label layout (sender, subject, HH:MM, preview) are English-display-language assumptions. Other languages degrade to no unread count and no notifications, silently. The labels also contain invisible characters and concatenate without separators ("Inbox53unread"), so matching is containment-based, never prefix or word-boundary.
- **A toast click travels desktop, then Rust, then the page.** Each toast carries a `default` action, and its notify-rust handle waits on its own thread (`wait_for_action`) until the toast is clicked or closed. A click is handed to the main thread, which shows the window, activates the profile, and calls WebKit's `clicked()` on the stored WebKitNotification, which fires the page's `Notification.onclick`; `unread_title.js` opens the message there by replaying mousedown, mouseup and click on the message row, since OWA selects on mousedown. Rows that OWA has since re-rendered are skipped (`isConnected`), so the click then only brings the inbox forward. One thread per toast until it closes is the cost; persistent toasts hold a thread, which is fine at mail volumes.
- **The app runs native Wayland and removes tao's header bar.** tao installs its own GtkHeaderBar on every Wayland window (tall, no app icon). Plain GTK3 negotiates server-side decorations with KWin fine, so open_main and open_compose_window build the window hidden, call set_titlebar(None) and only then show it; set_titlebar is ignored once the window is realized. Up to 0.4.3 the app forced GDK_BACKEND=x11 instead, which broke pasting (next entry).
- **Never force XWayland again: it breaks Ctrl+V from other apps.** KWin's Xwayland clipboard bridge offers only the legacy atoms UTF8_STRING, TEXT and STRING, while WebKitGTK's GTK3 clipboard code checks for the literal format names text/plain or text/plain;charset=utf-8. The paste event then sees no types and the rich editor inserts nothing; Ctrl+Shift+V worked because OWA reads the text directly. Upstream WebKitGTK bug; on native Wayland the mime names come through and paste works.
- **Custom icons are decoded by gdk-pixbuf, not the image crate.** That is what makes SVG work: the librsvg pixbuf loader renders it at 512 px. Every GTK desktop ships that loader and the AppImage bundles it from the build host (librsvg2-dev is installed there). The image crate only resizes, badges and encodes PNG.
- **A custom icon cannot be applied to the window at runtime on Wayland.** `set_icon` is honoured on X11 only; KWin takes the Wayland window icon from the desktop file, which points at the icon theme. That is why Settings offers the icon theme copy instead of pretending the window icon changed, and why the copy only shows on the next start. The tray icon is the one place the custom PNG applies live.
- **The window icon on Wayland depends on the .desktop file name.** KWin resolves the icon by matching the Wayland app id (the binary name, outlook-for-linux) to a desktop file of the same name. Tauri names that file after productName, so productName is outlook-for-linux and the launcher label lives in Name= in main.desktop. Rename productName and the icon silently turns into the generic Wayland logo.
- **Notification filtering happens in Rust, not in the page.** The page raises a Notification for every new row regardless of settings; the show-notification handler reads config.json on each one (cheap) and drops it when notifications are off for the app or that profile, or when the window is focused and only_when_hidden is set. It returns true either way, otherwise WebKit would show its own toast. The preview is cut by dropping all lines after the first, which relies on `unread_title.js` putting the subject on line one.
- **The unread badge is a title heuristic, and the app writes the title itself.** OWA stopped putting the "(N)" count in the tab title (reproducible in Firefox), so `unread_title.js` reads the count from the folder pane and writes the prefix; the Rust title watcher then parses it for the tray badge. If Microsoft reshuffles the folder-pane DOM, badge and notifications both silently stop, nothing errors. Verify against a real unread mail after any Microsoft UI refresh.
- **Left-clicking the tray icon opens the menu, it does not restore the window.** That is how libayatana-appindicator works on Linux (no click events reach the app); restore is the menu's Open item. Do not try to add an on_tray_icon_event handler for clicks, it never fires here.
- **Tray menu shortcut text is a tab in the label; the keys themselves belong to the menubar.** muda registers menu accelerators only for window menubars, so a tray item never shows one. The labels carry "Hide\tCtrl+H" etc.; Plasma's menu renderer draws the part after the tab as a shortcut column (GNOME shows it as plain spacing). The real accelerators are declared on the menubar items with the same ids, and muda binds them on the GTK window, where they fire before the webview sees the key: they shadow OWA's own Ctrl+R (reply) and Ctrl+Q (mark as read), same keys as teams-for-linux on purpose. Keep a tray label and its menubar twin on the same key. Open has no key: a window-level accelerator cannot fire while the window is hidden.
- **The main window is a plain Window with child webviews, behind Tauri's `unstable` feature.** The profile switcher needs several isolated OWA webviews in one window, which only `Window::add_child` gives. On Linux a child is packed into tao's vertical GtkBox below the menubar and expands to fill it, so no bounds arithmetic is needed and the menubar height takes care of itself. `unstable` means the API may change between Tauri minor versions, not that it is broken. The webview label (profile-default) differs from the window label on purpose: a child with the window's own label makes Tauri treat the pair as a fused WebviewWindow.
- **Edit menu items drive WebKit editing commands, and carry no accelerators.** muda's predefined Cut/Copy/Paste/Select All synthesise key presses through libxdo on Linux, which does nothing on Wayland. The items are ordinary entries routed to `execute_editing_command`. No accelerator on them, or Ctrl+C/V/X/A would be intercepted at the window and never reach the page.
- **The profile switcher is a GTK item appended to muda's menubar.** Tauri keeps the GtkMenuBar private, so add_profile_switcher walks the GtkWindow's widget tree after set_menu, appends a `gtk::MenuItem` and right-justifies it with `set_right_justified`. That setter is deprecated in GTK3 but GTK3 is frozen, and GTK4 is not an option for wry. Its dropdown is a GTK menu rather than a muda submenu because the entries need coloured status dots, which muda labels cannot draw.
- **Profiles are webviews, not windows, and unloading is `Webview::close`.** Each profile's child webview has its own data directory, which gives it its own WebContext (cookies, storage, network process); Tauri refcounts contexts per webview, so closing the last webview on a directory drops the context and its processes too. That is the whole memory saving; hiding a webview saves nothing, WebKit keeps the page alive. Two things do survive an unload on purpose or by WebKit's design: the profile's network process (Tauri keeps every WebContext alive for the life of the app on Linux, tauri issue 14626, about 45 MB each), and, without help, the web process itself: WebKit moves a closed page's process into its process cache for up to 30 minutes with the memory still allocated. `unload` therefore calls `terminate_web_process` before closing the webview. Verify with `ps -C WebKitWebProcess`: after an unload only the selected profile's large process may remain. Never set a profile's data directory to another profile's: same directory means the same cookie jar and the same account.
- **The `default` profile points at the pre-profile data directory on purpose.** Tauri's default webview data directory on Linux is `app_local_data_dir`, and that is where the single session lived before profiles. Mapping `default` to that exact path (not to `profiles/default/`) is what makes the upgrade keep the sign-in. Changing it logs everyone out.
- **The profile dropdown is rebuilt in full after every change, but never while it is open.** Rebuilding is simpler than patching labels, and cheap. The dropdown is one persistent GtkMenu whose entries are replaced in place; while `is_visible` says it is popped up, the refresh only marks it dirty and the menu's hide signal redoes it. The first version swapped in a fresh menu on every unread update, and an update that landed while the dropdown was open destroyed the menu holding GTK's pointer grab: a flood of `_gtk_widget_captured_event` criticals and an app that takes no input. Never call show on the menu widget itself, GTK does that on popup and it is what `is_visible` keys on. The entry handlers also run through `idle_add_local_once`, so no handler touches the menu it was fired from, and `set_active` on a CheckMenuItem fires `activate`, so it is set before the handler is connected.
- **Profile ids are never reused, hence the random suffix.** Tauri keeps every WebContext alive for the life of the app (see above), and WebKit's network process holds that profile's cookie jar in memory. Deleting the directory does not empty it. A removed profile re-added under the same directory name would therefore come back signed in as the removed account, so `unique_id` appends four random hex digits and `data_dir` never maps two ids to one path. The `default` id is the one exception, and it maps to the shared base directory: removing it deletes that directory's entries except `profiles/`, never the directory itself.
- **The Settings window must not be modal.** KWin routes activation and close requests for a window to its modal child, so with a modal Settings open the taskbar's Close on Outlook never reached the main window and nothing happened. Settings is a plain transient window; the main window's close handler closes it before hiding to the tray. Dialogs opened while it is open are still parented to it (`app_icon::dialog_parent`), so they appear in front of it.
- **Settings pages rebuild instead of updating widgets.** Setting a GTK check button or combo programmatically fires its changed signal, which would re-apply the config and loop. Each page is a function from config to widgets, created in their final state before any handler is connected, and re-run after every change. Cheap, and no signal blocking needed.
- **config.json is written whole; every writer goes through `config::update`.** The icon picker used to save a struct with only `app_icon`, which would now wipe the profiles. Read, change, write, never construct a fresh Config to save.
- **One menu handler for tray and menubar.** Tauri registers the tray's `on_menu_event` as a global menu listener, so it receives menubar events as well. Shared ids (hide, refresh, quit) are the same action by design. Do not add a second `app.on_menu_event` for the menubar, every shared id would fire twice.
- **Quit must go through app.exit.** The main window's CloseRequested is intercepted to hide instead; app.exit(0) bypasses that. If quit ever seems broken, check nobody "simplified" it to window.close().
- **New-window requests (target=_blank links in emails, window.open) go to the system browser.** WebKitGTK emits `create` for these and, with no handler, the request dies silently: the link looks dead. The builder's `on_new_window` hands http(s) URLs to `xdg-open` and always answers Deny, so the app never spawns a second webview. Non-http schemes are dropped on purpose.
- **`javascript-can-open-windows-automatically` must stay on.** OWA's link click handler awaits a Safe Links lookup before calling window.open, so the call runs outside the user gesture and WebKitGTK blocks it silently by default: first click does nothing, second click (lookup cached) works. The setting is harmless here because the new-window handler never creates a webview.
- **Icon filenames must stay RGBA.** tauri-build rejects non-RGBA PNGs; regenerate with ImageMagick using the `PNG32:` output prefix.
- **AppImage bundling needs `NO_STRIP=true`.** linuxdeploy ships a binutils too old for the `.relr.dyn` relocations in Fedora's shared libraries; its strip step fails on every library and Tauri reports only "failed to run linuxdeploy". The npm build script sets the variable; the deb and rpm are unaffected. The AppImage is a bit larger as a result.

## Update Now: file names and pkexec

`update.rs` downloads `outlook-for-linux-<v>-1.<arch>.rpm`, `outlook-for-linux_<v>_<amd64|arm64>.deb` or `outlook-for-linux_<v>_<amd64|aarch64>.AppImage` plus `SHA256SUMS` from the release. Those are the names the Tauri bundler and release.yml produce; a rename there breaks Update Now silently (a 404 shows as a failed download). Installs go through `pkexec`, which shows the desktop's own password prompt; `sudo` has no terminal here. The install is detected on the check thread (`dnf repoquery` can take a second), never on the main thread. After the install the new binary is spawned detached and the app exits; the AppImage keeps running from its mounted old file during the rename. The update state is a thread_local on the main thread and Settings rebuilds its Updates page through `settings::redraw` whenever it changes.

## Window::show shows every child webview

tao implements `Window::show` with `gtk_widget_show_all`, so a hidden background profile webview reappears under the active one, splitting the window in two. Every path that shows the main window (`show_main`: tray Open, second launch, toast click) calls `profiles::hide_inactive` right after.

## Compose windows end with an empty window

After Send or Save, OWA calls `window.close()`, which WebCore allows here because the compose window has a single history entry. WebKit raises the `close` signal; wry's handler destroys the WebKitWebView widget and stops there, so the Tauri window stays open with nothing in it. No navigation, title change or close request reaches the app. `open_compose_window` hooks the widget's `destroy` signal and closes the window from an idle callback.
