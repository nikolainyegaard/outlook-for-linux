# Gotchas

- **WebAuthn does not exist in webkit2gtk-4.1 as shipped by Debian 13 (tested 2.52.5).** `PublicKeyCredential` is undefined; there is no `enable-webauthn` property and no WebAuthentication feature flag (verified via GIR and a live JS probe). Upstream only builds WebAuthn for the GTK4 port (webkitgtk-6.0), which wry/Tauri cannot use yet. That is why the app ships its own implementation (polyfill + Rust CTAP2 client); see architecture.md.
- **Microsoft hides the passkey option based on user-agent sniffing.** With WebKitGTK's default UA the login page shows "Use an app instead" and never calls any WebAuthn API, even when `PublicKeyCredential` exists. The Chrome-on-Linux UA set in main.rs is load-bearing; remove it and passkey sign-in silently disappears with no error anywhere.
- **main.rs still sets `enable-webauthn` via GObject property, guarded by `has_property`.** Future-proofing only: if a WebKitGTK build ever ships the property, native WebAuthn gets enabled too. Keep the guard: `set_property` on a missing property is a hard panic.
- **The ACL permission is autogenerated.** build.rs declares `webauthn_get_assertion` in the app manifest, which generates `permissions/autogenerated/` (gitignored). Without the build.rs declaration, remote pages get a permission error on every invoke: remote origins always go through the ACL.
- **Polyfill runs in the main frame only.** Tauri injects its IPC internals main-frame-only, so an iframe-embedded login flow would see a polyfill with no IPC; the polyfill is therefore main-frame-only on purpose. If Microsoft ever moves sign-in into an iframe, this breaks.
- **Sign-in only.** `navigator.credentials.create()` throws NotSupportedError. Register new keys in a regular browser, then sign in here. USB keys only; no phone QR (hybrid) flow.
- **`frontendDist` is a URL on purpose.** There is no local dist folder. Tauri accepts a URL here for remote-only apps; do not "fix" it by adding a dist directory. Side effect: outlook.office.com counts as a *local* URL in the ACL, which is why capabilities/webauthn.json uses `local: false`.
- **Never launch with `WEBKIT_DISABLE_DMABUF_RENDERER=1` by default.** It forces WebKitGTK onto software rendering and makes the whole app sluggish (confirmed on Intel iGPU: dropping it closed most of the perceived gap to Electron wrappers). It is first aid only, for a blank window on a broken GPU stack, and belongs in a user's environment, not in the app or docs examples.
- **The custom main.desktop template exists because of a missing `%u`.** Tauri's default .desktop template adds the mailto MimeType from the deep-link config but generates `Exec=outlook-for-linux` without `%u`, so a clicked mailto link would launch the app with no URL argument. If you drop the template, mailto handling silently breaks; verify by extracting the .deb and reading the Exec line.
- **mailto flow**: the .desktop registers x-scheme-handler/mailto; a second launch is forwarded by the single-instance plugin to the running app, which opens a compose window via OWA's deeplink URL. Sequential window labels (compose-0, compose-1) are required: reusing a label is an error while the old window exists.
- **OWA never raises web notifications here; the app fakes them from the DOM.** Its service worker disqualifies WebKitGTK before ever calling showNotification (no push service), and WebKitGTK would not deliver service-worker notifications to the embedder anyway (only the page-context `Notification` constructor reaches the show-notification signal; verified empirically). The OWA notification setting is therefore irrelevant. `unread_title.js` polls the folder pane and message list instead; see architecture.md.
- **New-mail parsing is anchored to English OWA labels.** "Inbox", "unread" and the aria-label layout (sender, subject, HH:MM, preview) are English-display-language assumptions. Other languages degrade to no unread count and no notifications, silently. The labels also contain invisible characters and concatenate without separators ("Inbox53unread"), so matching is containment-based, never prefix or word-boundary.
- **Notification clicks do nothing.** Notifications are forwarded to DBus via notify-rust; focusing the app on click would need action handling with a blocking wait per notification. Add it if it starts to matter.
- **The app forces `GDK_BACKEND=x11` (XWayland) on purpose.** GTK3 on Wayland draws its own tall client-side titlebar and cannot use KWin's decoration protocol; under XWayland the window manager draws the slim system titlebar with the app icon, matching Electron apps (which also default to XWayland). Shrinking the GTK CSD bar via CSS was tried and did not take. The env check respects a user-set GDK_BACKEND. Revisit if wry moves to GTK4, which decorates properly on Wayland.
- **The unread badge is a title heuristic, and the app writes the title itself.** OWA stopped putting the "(N)" count in the tab title (reproducible in Firefox), so `unread_title.js` reads the count from the folder pane and writes the prefix; the Rust title watcher then parses it for the tray badge. If Microsoft reshuffles the folder-pane DOM, badge and notifications both silently stop, nothing errors. Verify against a real unread mail after any Microsoft UI refresh.
- **Left-clicking the tray icon opens the menu, it does not restore the window.** That is how libayatana-appindicator works on Linux (no click events reach the app); restore is the menu's Open item. Do not try to add an on_tray_icon_event handler for clicks, it never fires here.
- **Quit must go through app.exit.** The main window's CloseRequested is intercepted to hide instead; app.exit(0) bypasses that. If quit ever seems broken, check nobody "simplified" it to window.close().
- **New-window requests (target=_blank links in emails, window.open) go to the system browser.** WebKitGTK emits `create` for these and, with no handler, the request dies silently: the link looks dead. The builder's `on_new_window` hands http(s) URLs to `xdg-open` and always answers Deny, so the app never spawns a second webview. Non-http schemes are dropped on purpose.
- **Icon filenames must stay RGBA.** tauri-build rejects non-RGBA PNGs; regenerate with ImageMagick using the `PNG32:` output prefix.
